# Совет моделей для исполнителя

Исполнитель — модель, которой пользователь поручил задачу. Совет — три модели разных семейств,
которые отвечают на один вопрос независимо в одноразовых снапшотах репозитория, судья из другого
семейства, который выбирает самое простое из корректных решений или предлагает своё, если знает
решение лучше всех предложенных, и опровергатель, который обязан
опровергнуть каждое утверждение уликой из кода или тестом. Модели не спорят между собой: спор в
раундах ухудшает ответы, независимость плюс судья — улучшает (см. `references/method.md`).

Ниже `Q=~/.claude/skills/quorum/bin/quorum`; путь подставь по установке.

## Когда исполнитель спрашивает совета

Фраза пользователя «реализуй X и проси совета у codex, grok, glm» включает три точки. Не больше.

1. **До кода, всегда.** Прочитал задачу и код, написал план на полстраницы с местом, где есть
   выбор. `--stage plan`. Выбранный вариант и список «обязательно сделать» из вердикта идут в план.
2. **В середине, не больше одного раза, только по условию.** Тест или проверка падает, и причина
   не понята с двух попыток. `--stage stuck`. Вопрос узкий: команда, ожидание, что вышло, что пробовал.
3. **Перед словом «готово», всегда.** `--stage done`. Советники запускают тесты, линтеры и e2e из
   брифа сами и называют только блокирующее; опровергатель отсеивает недоказанное. Исполнитель
   чинит подтверждённое и заканчивает.

Если пользователь попросил только «спроси совет по вопросу Y», это одна точка 1 без реализации.

## Советники и судья из фразы пользователя

Каждого советника и судью записывай как `ИМЯ[=МОДЕЛЬ][@УРОВЕНЬ]`. Уровень — effort, уровень
рассуждений этой модели. Советники идут через запятую.

| Во фразе пользователя | В команде |
|---|---|
| grok-4.7 xhigh, glm-5.3 max | `--advisors grok@xhigh,glm@max` |
| opus 5.5 xhigh, kimi-k2.8 max | `opus@xhigh,kimi@max` |
| chatgpt-6 ultra | `codex@ultra`: модель Codex по умолчанию, `gpt-6-astra` |
| gpt-6.1-sol max | `codex=gpt-6.1-sol@max` |
| судья fable 5.1 high | `--judge fable@high` |

- Модель после `=` пиши только тогда, когда пользователь назвал не ту, что стоит по умолчанию
  (`$Q config`). Номер версии в имя не добавляй: CLI не знает `opus-5.5`, а `opus` — это последняя
  Opus.
- Один бэкенд дважды: `codex:a@high,codex:b@ultra`.
- Без указаний берутся `QUORUM_ADVISORS` и `QUORUM_JUDGE`.
- Переменные окружения вроде `CODEX_EFFORT=…` перед командой больше не нужны.

Советник, который не смог стартовать (неизвестная модель, неверный уровень, нет входа), получает
статус `failed` с причиной в `$Q status` и попадает в раздел вердикта «Не ответили». Не подменяй
его молча: скажи пользователю и продолжай с остальными. Если он нужен, запусти его отдельным
прогоном с исправленной записью.

## Порядок действий

1. **Бриф.** `$Q brief` печатает шаблон. Заполни его и запиши новым файлом
   `/tmp/quorum-<проект>.md`: задача, что сделано, один вопрос, команды проверки, цена ошибки,
   известные решения. Дифф и код не вкладывать. Шаблон без своего текста `consult` не примет.
   `--out FILE` сразу пишет шаблон в файл; если твой инструмент записи требует прочитать файл перед
   перезаписью, прочитай его. Раздел `## Quorum` (или `## Совет`) из `AGENTS.md`/`CLAUDE.md`
   проекта подставляется сам.
   Всё, что пользователь дал для проверки руками — curl с токеном, адрес стенда, тестовую базу,
   пример запроса — переноси в раздел «Пробы» брифа дословно: советники выполнят это сами и
   сверят ответ ручки с ожиданием. Бриф живёт в каталоге прогона и удаляется с ним; в заметку
   `feedback` и в журнал секреты не попадают.
2. **Запуск из корня репозитория.** `$Q consult --brief /tmp/quorum-<проект>.md --stage plan
   --advisors grok@xhigh,glm@max --judge fable@high` (по умолчанию `codex,grok,glm` и `fable`;
   `--plan design.md` кладёт документ в снапшот). Снапшот включает незакоммиченные правки.
   Сохрани напечатанный путь прогона. Ушёл не тот бриф или не те советники — `$Q clean RUN --force`
   останавливает и удаляет прогон.
3. **Ждать.** Прогон идёт сам: судья, повторный круг и опровергатель запускаются, как только
   закончит предыдущая роль. Первая строка `$Q wait RUN --max 110` — ровно `STATE: ready` или
   ровно `STATE: running`; путь к вердикту и состояние ролей идут ниже. Сравнивай первую строку
   целиком. Код возврата в обоих случаях 0: `running` — не ошибка, но и вердикта ещё нет: не
   читай каталог прогона, не пиши `feedback` и не вызывай `clean`, пока не увидел `STATE: ready`.
   Если твой инструмент умеет запускать команду в фоне и сообщать, когда она закончится (в Claude
   Code — `run_in_background`), запусти один `$Q wait RUN --max 3600` в фоне. Иначе зови
   `$Q wait RUN --max 110` снова. Между вызовами делай только то, что не зависит от ответа: в точке
   1 и 3 ждать, в точке 2 можно работать над несвязанной частью. Прогон занимает 15–60 минут,
   отдельный советник может думать дольше остальных.
4. **Читать вердикт.** `RUN/verdict.md`: выбор судьи — буква советника или «своё решение» судьи,
   если он знает решение лучше всех предложенных; «обязательно сделать», «не брать», проверка
   выбранного решения опровергателем; ответы советников с разделом «Что отбросил» — по нему
   отвечай на «а почему не X?». На приёмке — подтверждено / опровергнуто / не проверено.
   Опровергнутые находки не чинить; они перечислены, чтобы пользователь мог вернуть их рукой.
   «Не проверено» решает исполнитель по коду. С `--no-refute` на приёмке все находки попадают в
   «не проверено».
5. **Действовать в рамках задачи.** Взять выбранное решение целиком, не добавлять «не брать».
   Уточнение у одного советника: `$Q ask RUN codex "вопрос"`, у судьи: `$Q ask RUN judge-1 "вопрос"`.
6. **Записать заметку и убрать за собой.** `$Q feedback RUN "что помогло, что принято, что
   отклонено"` — одна-три строки, они нужны для ретроспективы; без вердикта команда откажет.
   Затем `$Q clean RUN`; пока задания идут, он откажется, и это правильно: дождись `STATE: ready`.

## Что не делать

- Не запускать совет на каждый шаг и не добавлять четвёртую точку «на всякий случай».
- Не пересказывать советникам чужие ответы и не устраивать раунды спора: у судьи есть один
  повторный круг, когда приемлемого решения нет, и этого достаточно.
- Не принимать находку без улики `ran` или `read`. Совпадение мнений моделей — не улика.
- Не использовать скилл external-review: он снят с использования.

## Команды и файлы

| Команда | Назначение |
|---|---|
| `$Q doctor` / `$Q config [set K V]` | доступные бэкенды; советники, судья, модели, effort |
| `$Q consult --brief F --stage plan\|stuck\|done` | запуск; `--advisors ИМЯ[=МОДЕЛЬ][@УРОВЕНЬ],…`, `--judge`, `--plan`, `--base`, `--no-refute`, `--deps` |
| `$Q wait RUN [--max SEC]` / `$Q status RUN` | подождать вердикт; прогресс по ролям |
| `$Q clean RUN --force` | остановить прогон и удалить его |
| `$Q ask RUN JOB "вопрос"` | продолжить сессию советника |
| `$Q feedback RUN "заметка"` / `$Q digest [--since D]` | заметка исполнителя; журнал для ретроспективы |
| `$Q clean [RUN\|--all]` | удалить снапшоты и прогон |

- `prompts/ru/`: `plan.md`, `stuck.md`, `done.md` (советники), `judge.md`, `refuter.md`, `brief.md`.
- `references/setup.md`: установка, ключи, смена моделей. `references/backends.md`: флаги CLI.
- `references/method.md`: почему так устроено и что говорят исследования.
- Журнал: `~/.local/state/quorum/usage.jsonl`, заметки: `feedback.jsonl`, прогоны: `runs/`.
